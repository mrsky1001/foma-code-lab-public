## 3. Анализ Frontmatter и требования к его сохранению (Safe Edit)

### 3.1. Как приложение парсит Frontmatter

Парсинг frontmatter осуществляется плагином `plugins/vite-plugin-lessons.ts` с помощью регулярного выражения:
```typescript
const fmMatch = content.match(/^---\r?\n([\s\S]*?)\r?\n---\r?\n([\s\S]*)$/);
if (!fmMatch) throw new Error(`No YAML front-matter in ${filePath}`);
const meta = yaml.load(fmMatch[1]) as Record<string, unknown>;
```

Извлекаются три атрибута:
1. `title`: Строковое название шага (отображается в боковом меню тренажёра и в заголовке вкладки).
2. `highlight`: Активная вкладка редактора (`html`, `css` или `js`).
3. `type`: Тип шага (`theory` или `practice`).

Далее в `src/lessons/index.ts`:
```typescript
function stepType(step: LessonStep, lessonId: number): 'theory' | 'practice' {
  if (step.type) return step.type;
  return lessonId === 1 ? 'theory' : 'practice';
}
```

### 3.2. Риски повреждения Frontmatter

1. **Сбой регулярного выражения `fmMatch`:** Если разделитель `---` будет сдвинут, пробелен, заменён на `***` или удалён, Vite выбросит `Error: No YAML front-matter in <file>` и сборка упадёт.
2. **Сбой YAML-парсера:** Нарушение отступов, незакрытые кавычки в `title`, недопустимые спецсимволы приводят к краху `yaml.load`.
3. **Ложная мутация типа шага (`type`):**
   - Если практический шаг потеряет `type: practice` (или превратится в `theory`), функция `accumulatePractice` исключит его из цепочки, и код этого шага не будет передан в последующие шаги.
   - Если теоретический шаг получит `type: practice`, его тестовый изолированный код попадет в общую базу «СмартОфиса» и сломает всю последующую верстку.

## 4. Архитектура блоков кода в Markdown

В каждом файле контента присутствуют два типа блоков кода:

### 4.1. Демонстрационные блоки теории
Оформляются стандартными блоками Markdown:
````markdown
```html
<p>Пример параграфа</p>
```
```css
body { margin: 0; }
```
```js
console.log('Тест');
```
````
Они отображаются как подсвеченный код внутри текстовой статьи.

### 4.2. Интерактивные блоки тренажёра (Editor Workspaces)
Оформляются специальными мета-тегами:
- ```` ```html:start ```` и ```` ```html:solution ````
- ```` ```css:start ```` и ```` ```css:solution ````
- ```` ```js:start ```` и ```` ```js:solution ````

**Критическое правило парсера:**  
В `plugins/vite-plugin-lessons.ts` граница между теоретическим описанием (`explanation`) и редактором вычисляется по первому вхождению:
```typescript
const firstBlockIdx = body.search(/^```\w+:(start|solution)/m);
const explanation = (firstBlockIdx === -1 ? body : body.slice(0, firstBlockIdx)).trim();
```
Если при редактировании теории будет случайно вставлен тег `:start` или `:solution`, парсер сочтёт это началом редактора и обрежет весь последующий текст теории!

## 6. Стратегия и архитектура автоматизированного верификатора (Verification Strategy & Test Harness)

Для выполнения критериев приемки из `ORIGINAL_REQUEST.md`:
- **Критерий 1:** Все 113 проблем из отчёта применены к исходным файлам.
- **Критерий 2:** Программный скрипт верификации подтверждает полное покрытие и целостность разметки оставшегося текста.

Предлагается реализовать специализированный автоматизированный тестовый харнес (например, `scripts/verify-113-applied-fixes.py` или `.mjs`), состоящий из **5 уровней проверок (5-Layer Validation Pipeline)**.

```
┌────────────────────────────────────────────────────────────────────────┐
│               5-LAYER TEST HARNESS ARCHITECTURE                        │
├────────────────────────────────────────────────────────────────────────┤
│ Layer 1: Git & Inventory Oracle (111 mod, 120 pristine, 0 lost/added)  │
│ Layer 2: Frontmatter & YAML Invariance Validator (225 fixed, 6 updated)│
│ Layer 3: Markdown & Code Fence Syntactic Guard (balanced ```, valid)   │
│ Layer 4: Semantic Fix Oracle (113/113 verified: "Было" 0, "Стало" 1)  │
│ Layer 5: Runtime & Build Compilation Pipeline (Vite, JS, Headless E2E) │
└────────────────────────────────────────────────────────────────────────┘
```

### 6.1. Layer 1: Git & File Inventory Oracle (Контроль охвата и неприкосновенности)

1. **Контроль затронутых файлов:**
   - Команда `git diff --name-only content/lessons` должна вернуть **ровно 111 уникальных файлов**.
   - Каждый из 111 файлов обязан входить в официальный список файлов с замечаниями из `content/AUDIT_REPORT.md`.
2. **Контроль чистых файлов (Pristine Guard):**
   - Ни один из 120 файлов со статусом «Без замечаний» не должен присутствовать в `git diff`.
   - Любое изменение в файле из списка 120 расценивается как `CRITICAL_FAILURE`.
3. **Контроль структуры каталога:**
   - Количество `.md` файлов должно оставаться ровно **231**.
   - Количество `_lesson.yml` файлов должно оставаться ровно **10**.
   - Никакие временные файлы (`.bak`, `.tmp`, `.orig`) не должны появиться в `content/lessons/`.

### 6.2. Layer 2: Frontmatter & YAML Invariance Validator (Защита метаданных)

1. Для каждого из 231 `.md` файла:
   - Проверяется наличие открывающего `---` на строке 1 и закрывающего `---`.
   - Производится разбор через `yaml.load()`.
   - Для **225 файлов** (105 исправляемых + 120 чистых):  
     Блок строк между `---` и `---` побайтово сравнивается с эталоном из `git show HEAD:<path>`. Расхождение = `FAIL`.
   - Для **6 файлов** (из табл. 3.3):  
     Поле `title` обязано совпадать с `HEAD`. Поле `type` обязано быть `theory` для `09-final/10-final-congratulations.md` и `practice` для пяти файлов `10-troubleshooting`. Поле `highlight` обязано совпадать с `HEAD`.

### 6.3. Layer 3: Markdown & Code Fence Syntactic Guard (Целостность разметки)

1. **Баланс обратных кавычек:**
   - Число строк, начинающихся с ```` ``` ````, обязано быть строго чётным в каждом файле.
2. **Валидность служебных блоков тренажёра:**
   - Все блоки вида ```` ```{lang}:{variant} ```` должны иметь `variant` только `start` или `solution`, а `lang` только `html`, `css` или `js`.
   - После каждого открывающего блока тренажёра обязан следовать закрывающий ```` ``` ````.
3. **Сохранение заголовков задач:**
   - В практических шагах должен сохраняться заголовок `## 🛠 Задание`.

### 6.4. Layer 4: Semantic Fix Oracle (Семантический верификатор 113 исправлений)

Это ключевой слой, подтверждающий, что каждое из 113 исправлений действительно применено, а не просто изменены случайные строки.

1. **Методика парсинга требований аудита:**
   Из `content/AUDIT_REPORT.md` для каждого из 113 пунктов извлекаются:
   - Целевой файл (`**Файл:**`).
   - Исходные ошибочные строки или фрагменты («Было: ...»).
   - Целевые правильные строки или фрагменты («Стало: ...»).
2. **Двусторонняя проверка (Negative + Positive Assertions):**
   - **Negative Assertion:** Файл проверяется на отсутствие устаревшего / ошибочного фрагмента.

   - **Positive Assertion:** Файл проверяется на присутствие исправленного фрагмента.

## 7. Риски и рекомендации для исполнителей (Worker Agents)

1. **Не использовать полностроковую перезапись крупных файлов:**
   В уроках 06–08 файлы достигают 1 500 – 1 600 строк. Перезапись файла целиком несёт риск потери кода кумулятивной цепочки. Рекомендуется использовать точечную замену конкретных строк или блоков (`replace_file_content`).
2. **Соблюдать единообразие пробелов и переводов строк (CRLF vs LF):**
   Файлы в Windows-окружении содержат переводы строк CRLF. Редакторам необходимо сохранять оригинальный стиль переноса строк, чтобы diff оставался чистым и не содержал паразитных изменений всего файла.
3. **Не трогать чистые файлы:**
   Перед началом работы каждый исполнитель должен свериться со списком 120 чистых файлов. Изменение любого из них является нарушением регламента Safe Edit.
4. **Контролировать файлы с 2 проблемами:**
   Особое внимание уделить файлам `04-js-dom/00-theory-01-js-basics.md` и `04-js-dom/00-theory-05-create.md`: в них требуется применить **обе** описанные в отчёте правки.
